# 综合应用实践与项目交付类结构模板

这份模板适合阶段综合练习和完整项目。项目大小由学习成果决定，不以技术数量和代码行数衡量。

## 使用前填写

- 用户或系统目标：`[...]`
- 起始资产与当前可运行状态：`[...]`
- 已学技术与允许提供的支架：`[...]`
- 交付物、验收方式和停止条件：`[...]`
- 依赖服务、版本、端口与数据：`[...]`
- 范围外需求和非目标：`[...]`

## 项目入口

1. 用具体使用场景和输入输出定义项目，不写宏大背景。
2. 展示最终行为或最小验收样例。
3. 说明架构边界、起始代码、运行方法和已知限制。
4. 把工作拆成可以独立验证的纵向切片或里程碑。

## 路径 A：纵向切片

先完成一条最小端到端路径，例如一个请求从入口到数据层再返回结果。随后按真实需求增加校验、持久化、安全、缓存、消息、前端或部署。每次只扩展少量能力，并保持系统可运行。

## 路径 B：里程碑交付

每个里程碑使用同一组信息：

1. 当前要交付的行为。
2. 会修改的组件和它们的职责。
3. 关键步骤与必要代码。
4. 预期输出、测试或状态证据。
5. 常见失败、恢复方式和提交点。
6. 进入下一里程碑的条件。

## 路径 C：已有系统改造

1. 运行基线并保存性能、测试或行为证据。
2. 用新需求指出当前设计的限制。
3. 提出一到两个候选方案和选择标准。
4. 以最小改动实施，并解释跨层影响。
5. 对比改动前后，执行回归和失败测试。
6. 记录没有解决的问题和回退方式。

## 项目收束

1. 用统一命令或流程从干净环境重新运行。
2. 按验收契约检查功能、错误处理、数据状态和部署状态。
3. 安排一个没有逐行答案的迁移任务或故障修复。
4. 回顾技术选择、边界和后续改进，不逐文件复述实现。

## 正文与配套资产分工

正文突出决策、关键改动、验证和排错。完整项目文件放在配套资产中，通过明确路径引用。不要在正文重复粘贴未变化的样板代码；也不能只给仓库链接而省略关键教学步骤。

## 交付前检查

- 每个里程碑是否都能运行、验证并安全继续？
- 项目是否依赖尚未讲授的大量新技术？
- 学习者是否知道当前改动跨越了哪些组件，以及怎样观察结果？
- 验收是否覆盖正常路径、至少一个失败路径和干净环境复现？
- 最后的独立任务是否真正要求迁移，而不是替换名称？
