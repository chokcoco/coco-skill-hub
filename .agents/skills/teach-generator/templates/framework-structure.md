# 单一框架或工具介绍、应用及进阶类结构模板

这份模板适合一个框架、库或工具的独立教学单元。先形成最小闭环，再根据需求解释组件和扩展；不要从功能清单开始。

- 固定版本与初始化方式：`[...]`
- 最小闭环的输入和输出：`[...]`
- 本章不展开的扩展点：`[...]`

## 路径 A：首次建立最小闭环

1. 用一个输入输出说明框架在当前课程中的位置。
2. 解释项目中会出现的少量核心组件和文件。
3. 创建最小项目或加入最小依赖，保留能运行的必要配置。
4. 完成一条功能路径，并用响应、日志、测试或文件验证。
5. 沿执行链解释入口、框架接管的工作和用户代码的职责。
6. 修改一个条件，观察配置或组件变化。
7. 处理两个到四个真实常见的失败模式。
8. 说明下一章会扩展什么，以及当前方案的边界。

## 路径 B：在已有项目中增加能力

1. 复核现有项目状态和本章改动目标。
2. 找到框架接入点、配置来源和运行入口。
3. 用最小改动形成新能力，并保存改动前后的证据。
4. 拆解新增组件怎样进入原有执行链。
5. 增加校验、测试、日志或故障案例。
6. 让学习者独立改变一个需求，而不是复制第二份代码。

## 路径 C：进阶配置与扩展

1. 从默认行为的明确限制开始。
2. 建立默认执行模型，区分公开契约与常见实现。
3. 引入一个扩展点，解释注册时机、作用范围和覆盖关系。
4. 用对照实验验证配置生效。
5. 讨论冲突、顺序、性能、安全或维护边界。
6. 给出回退方式和适用判断，不把进阶配置包装成默认最佳实践。

## 可选模块

组件关系图、请求时序、配置对照表、调试观察、版本差异、迁移说明、API 查阅练习。只有当前闭环需要时才加入。

## 交付前检查

- 学习者是否先得到一个可运行结果，再逐步理解框架行为？
- 每个依赖、注解和配置是否都改变了可说明的行为？
- 框架自动完成的工作是否有入口、主链路和观测证据？
- 示例是否使用锁定版本真实运行，命令与结果是否一致？
- 进阶内容是否来自实际限制，而不是 API 数量？
