# 原理机制、协议、架构与故障诊断类结构模板

先选择“机制解释”“架构链路”或“故障诊断”为主任务。三条路径可以借用模块，但不能全部完整串联。

## 使用前填写

- 要解释或定位的现象：`[...]`
- 学习者已经掌握的模型：`[...]`
- 参与对象、状态和事件：`[...]`
- 规范保证、实现细节与教学简化：`[...]`
- 可使用的证据：`[日志 / 抓包 / 指标 / 实验 / 测试 / 源码]`
- 适用条件和不讨论范围：`[...]`

## 路径 A：机制解释与实验验证

1. 展示一个可重复观察的现象，并写明条件。
2. 定义参与对象和关键状态，补足必要前置。
3. 按时间、数据流或状态变化建立因果链。
4. 给出一个能区分两种解释的最小实验。
5. 观察结果并回到模型解释。
6. 改变一个条件，建立机制边界或反例。
7. 将结论迁移到设计、调试或性能判断。

## 路径 B：协议或架构链路

1. 确定系统边界、输入输出和参与方。
2. 选择一条真实请求或数据流作为主线。
3. 逐站说明职责、状态和交接信息。
4. 标出信任边界、失败点和可观测点。
5. 用日志、抓包、追踪或测试验证链路。
6. 比较一个替代设计，说明权衡和适用条件。

## 路径 C：故障诊断

1. 保存原始现象、预期结果、环境和完整错误。
2. 划定故障范围，列出少量可验证假设。
3. 为每个假设设计最小检查，并写明两类结果如何解读。
4. 按证据缩小范围，不同时修改多个变量。
5. 定位根因，区分触发条件与深层原因。
6. 实施最小修复，重跑原场景和相关回归。
7. 总结以后应保留的日志、指标、测试或防护。

## 图与代码的使用

图只保留当前因果链中的对象和关系。代码、配置和命令用于制造或验证现象，不为“技术课必须有代码”而出现。每个证据都要说明它支持或排除了哪个判断。

## 交付前检查

- 是否把事实、推断和教学简化明确分开？
- 学习者能否根据条件预测下一状态或选择下一项检查？
- 是否存在至少一个能验证机制或排除假设的真实证据？
- 正常路径、失败路径和适用边界是否足够支撑本章目标？
- 删除术语和图后，因果链是否仍能用完整句子说明？
