# 单一框架或工具介绍、应用及进阶类写法指引

## 适用范围

用于单个框架、库、平台或开发工具的入门、常用功能和进阶配置，例如 Web 框架、ORM、测试框架、安全框架或构建工具。章节应让学习者完成一个小闭环，并解释框架替他做了什么。

## 先限定框架边界

说明框架解决哪类问题、当前章节使用其中哪一部分、它依赖哪些语言或协议知识。不要从框架历史和功能大全开始，也不要让“自动完成很多事情”停留在宣传句。

确认版本、初始化方式、依赖配置和运行命令。所有行为断言以课程批准的官方资料和真实运行结果为准。

## 推荐推进方式

可以从最小闭环开始：认识输入输出 → 建立最小项目或配置 → 运行并观察 → 拆解关键组件 → 修改一个需求 → 解释执行链 → 处理常见失败 → 说明进阶入口。

也可以从已有项目中的一条真实路径开始：找到入口 → 跟踪框架调用 → 修改配置或扩展点 → 通过日志、测试或响应验证。此路径只适合前置项目已经建立的章节。

配置项不要一次全部列出。先保留能形成闭环的最小配置，再通过需求变化逐项加入。每增加一个注解、插件、依赖或中间件，都说明它改变了什么行为。

## 解释“自动化”

学习者至少应知道入口在哪里、核心组件各自负责什么、配置何时被读取、请求或数据经过哪条主链路。源码级细节只在能解释当前现象时出现。若章节重点转为内部机制或故障定位，应把“原理机制类”设为主类型。

## 完成证据

可使用运行结果、接口响应、测试、日志、生成文件、配置差异和故障修复。练习应改变一个真实条件，避免只让学习者复制第二个相同示例。

## 常见失败

- 罗列注解、API 和配置，没有形成可运行闭环。
- 只给完整项目代码，没有解释框架入口和职责。
- 把官方文档重新排版，缺少面向当前受众的取舍。
- 在入门章提前讲完所有扩展点和生产配置。
- 用“约定优于配置”“开箱即用”等口号替代可观察行为。
