# 环境安装与工具准备类写法指引

## 适用范围

用于运行时、编译器、IDE、包管理器、构建工具、数据库、容器、云 CLI 和本地服务等环境准备。完成标准是目标设备上出现可复现结果，不是读者“理解了安装原理”。

## 写作前先收集

- 支持的操作系统、CPU 架构、终端和权限条件。
- 课程锁定的版本、兼容范围和不支持的组合。
- 官方下载入口、安装说明和版本核验方式。
- 已安装、首次安装、版本冲突三类起点。
- 每一步的可观察结果，以及失败后最短的证据收集路径。

下载地址、控制台入口和当前步骤必须打开的官方页面直接放在操作句中。章末参考文献仍保留完整来源。

## 推荐推进方式

常见主线是：展示完成结果 → 解释工具分工 → 分系统安装 → 逐项核验 → 运行最小成果 → 排查版本或路径冲突 → 留下验收记录。

已有环境的受众也可以先核验：执行检查 → 按结果分流 → 只补缺失工具 → 统一版本 → 完成最终验收。

上述常见主线优先「展示完成结果」的原因是，对于部分已经安装好环境的人，可以通过这一步骤提前核验，如果通过可以不继续进行下面的流程，节约时间，目的是不要让已经配置好的学习者重复安装。

macOS 与 Windows 都在支持范围时，两套路径必须各自闭环。不要只替换命令名；下载包架构、环境变量、终端重启、目录格式和权限行为都可能不同。

## 解释到什么程度

工具首次出现时解释它是什么、为什么需要、和其他工具怎样配合。安装选项只解释会影响课程结果的部分。命令必须说明在哪个目录、用哪个终端执行，以及成功后会看到什么。

排错按依赖链从外到内进行，例如先确认文件存在，再确认 PATH，随后确认工具选择的运行时，最后检查项目配置。每次只改变一个变量，并要求保留版本输出和完整错误。

## 常见失败

- 写“自行安装”“其他系统类似”，没有给出可完成路径。
- 只提供下载链接，没有说明版本、架构和安装包类型。
- 只在 IDE 中运行成功，没有核验终端和构建工具。
- 大段解释历史与内部原理，实际安装步骤反而缺失。
- 把作者的推进提醒写进正文，却没有真实风险和原因。
- 使用可能过期的版本或链接，没有重新核验官方资料。
