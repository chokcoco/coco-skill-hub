# 原理阐述+结合已有源码进行教学类写法指引

## 适用范围

用于以项目现有可运行仓库作为教学参考时，用“先建立原理/概念/机制，再落到项目真实源码切片，最后对照教学实现与真实实现的差异”来组织章节。学习者不仅要理解原理，还要能看懂项目是怎样做的，以及教学版在哪些地方为降低认知负荷做了简化。

本节型最适合以下场景：

- 课程与某个已有项目强绑定（学员可访问源码），且教学主线是你独立实现的版本，项目源码作对照切片；
- 主题本身是对协议、框架、API、架构组件或系统边界的讲解，且真实代码中有完整的工程表达；
- 学员需要建立“原理 → 代码落点 → 真实工程取舍”的完整理解链，而不仅仅是跑通一段示例。

## 先确定源码可引用的边界

在写作前确认可以公开引用的源码范围：哪些文件、类、函数属于“已实现”、哪些属于“目标方向”、哪些是“教学简化”。所有引用必须区分这三种状态，不得将目标架构说成已实现。

真实源码中不得在正文泄露：

- 内部文件路径（用仓库相对路径如 `apps/api/app/provider.py`，不用 `/Users/...`）；
- API Key、凭据、本机配置细节；
- 运行日志、质量评分、内部迭代记录、生产侧交接文档；
- 具体人名、内部项目代号。

## 推荐推进方式：四段递进

1. **建立原理/概念** — 把本章要解释的机制或设计决策说清楚：它回答什么问题、变量和边界是什么、为什么需要它。这一步不出现项目源码，只用公开资料和最小教学示例支撑。
2. **教学最小实现** — 给出一段可运行（或用 Fake 可测试）的最小代码，完整表达原理的核心逻辑，但去掉生产必需的错误处理、并发、持久化和观测。
3. **项目真实源码切片** — 展示当前仓库中对应的真实实现片段，逐段指出它比教学版多了什么、保留了哪种工程判断（例如硬超时、错误信号分类、脱敏、哈希校验、租约等）。
4. **差异与边界** — 列出教学实现与真实实现的主要差异，说明为什么教学版省略了某些部分、真实版为什么需要这些额外的逻辑。同时明确哪些能力是项目设计目标但尚未实现的，防止学员误以为已就绪。

四段之中，第一、二段是原理教学的主体，第三、四段是源码对照的主体。不可跳段，也不可将四段机械模板化（例如每一节都标题写“1 原理”“2 最小实现”“3 真实源码”“4 差异”），而要根据内容自然融合。

## 每个教学代码块下方的源码引用备注

当正文出现教学代码块（或真实源码代码块）时，在其闭合后使用引用注释格式（`>`）追加信息。信息多、包含路径、收益与差异说明时，必须按下面的三段式换行，不能压缩成一句话：

```markdown
> 1. 对应源码：`apps/api/app/schemas.py`（MissionOutput、ChapterPlan、BlueprintOutput 等真实输出模型）。
> 2. 模块阅读收益：真实 Schema 如何用 Field(min_length/ge/le/max_length) 与 list[...] 约束模型输出、哪些字段必填、如何做版本兼容。
> 3. 当前源码注释：正文是精简教学版，真实文件面向完整 20 章系统。
```

三段分别说明：

1. 对应源码：给出仓库相对路径，如 `apps/api/app/providers/gateway.py`，并列出关键符号；
2. 模块阅读收益：说明读者读了这个文件或这些文件后能完整理解什么功能、知道什么具体实现方法；
3. 当前源码注释：说明这段正文与真实实现的关系，例如“教学版简化了什么”“真实实现还包含什么”“这是可运行代码还是错误示范”。

对于教学简化版本，第三段必须点明与真实代码的差异（例如“教学版省略了错误信号分类与硬超时加锁，真实实现另见 …的 invoke_structured”）。真实源码正片、学生本地项目树形这类非仓库代码块，也按同一三段式说明它对应哪些真实模块，避免读者误把教学工程树当作仓库结构。

不要在正文段落中重复这些引用信息，避免增加正文阅读负担。引用备注放在代码块下方，不抢占正文句号后的段落开头。同一章内所有源码备注必须使用同一套三段式编号，保持可扫描性。

## 与真实源码的差异对照

所有引用真实源码的段落，必须显著区分以下两种状态：

- **已实现**：代码在当前仓库里可运行并被现有测试验证的行为；
- **目标方向**：出现在设计文档（如 BE-TD、FE-TD）中但尚未完全实现的能力。

对目标方向的引用仅限于“这里未来计划这样设计”，不应描述为“当前项目已这样做”。

## 完成证据

- 学习者能画出原理的关键概念图并用教学版代码验证；
- 学习者能指出教学版与真实实现的关键差异，每条差异都有源码行号或模块名作为证据；
- 学习者能在自己的项目中替换或扩展真实实现中的一个边界条件（例如增加重试上限、修改权限矩阵），而不是全量复刻。

## 常见失败

- 把项目代码大段贴进正文而不解释每条逻辑为什么存在。
- 未区分“已实现”和“目标方向”，让学员以为某个设计文档里的特性已经可运行。
- 源码路径写成绝对本机路径、包含内部文件名或凭据。
- 代码块下方没有引用备注，只写了“真实代码见 xx”，读者不知道去读什么。
- 教学版与真实版都说了一遍，但未指出差异和省略理由，变成两套并行文档。
- 用“典型实现”“推荐写法”等模糊词替代表达项目具体做了什么。
